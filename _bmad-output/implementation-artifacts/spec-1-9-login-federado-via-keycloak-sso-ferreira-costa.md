## Intent

**Problem:** O stockflow só autentica por e-mail/senha. FR-34 / Story 1.9 pede login federado via Keycloak (realm corporativo `ferreiracosta`) como opção adicional, replicando o padrão já em produção no `FB_APU02` (AD-7). Hoje não há pacote `iam/`, nada valida token Keycloak, a tela de Login não tem botão de SSO, não existe rota de callback, e não existe nenhuma forma de logout (nem para o login por senha) — a AC5 exige RP-initiated logout ao encerrar uma sessão iniciada por SSO.

**Approach:** Backend: pacote `iam/` (cliente JWKS com cache em memória + middleware de validação RS256/`iss`/`azp`/`email_verified`); `handlers/auth_sso.go` com `GET /api/auth/sso/config` (config em runtime, `enabled` só se todas as env vars presentes), `POST /api/auth/sso/keycloak` (atrás do middleware `iam`; troca o access token do Keycloak por uma sessão própria via `EmitirSessao` — busca conta por e-mail case-insensitive, **nunca cria**) e `POST /api/auth/logout` (revoga a sessão do cookie de refresh + limpa cookie). Frontend: `lib/keycloak/` (Authorization Code + PKCE S256 manual, config buscada do backend), `AuthCallbackPage`, botão "Entrar com Ferreira Costa" na `LoginPage` (só quando `enabled`), `logout()` no `AuthProvider` (encerra sessão local; se veio de SSO, dispara RP-initiated logout) e item "Sair" no `AppShell`. Nenhuma migration nova. O provisionamento real do client Keycloak é ação de operador → `status: awaiting-operator`.

## Boundaries & Constraints

**Always:**
- Pacote `backend/iam/` isolado dos demais domínios (AD-7). `JWKSClient` thread-safe (`sync.RWMutex`): cache de chaves RSA em memória (TTL 1h), refetch quando o TTL expira **ou** o `kid` não está no cache; **JWKS com status != 200 ou zero chaves é erro, nunca sucesso** (dívida do `FB_APU02` explicitamente não repetida — addendum §B). Parse de JWK `kty=RSA` via `big.Int` de `base64.RawURLEncoding` de `n`/`e`. Refetch no máximo 1× por `GetKey` que erra o cache (sem amplificação por `kid` arbitrário). Usa `log/slog`, não `log`.
- Middleware `iam` (molde de `FB_APU02/backend/iam/iam_auth_middleware.go`, lido read-only): `Authorization: Bearer <token>` obrigatório; assinatura **RS256** via `kid`→JWKS (`jwt.WithValidMethods(["RS256"])` — qualquer outro `alg`, incl. `none`, rejeita); `exp` obrigatório (`jwt.WithExpirationRequired()`); leeway de 30s; `iss` == `IAM_BASE_URL` (URL do realm, comparação exata — a barra final é removida ao carregar a config); **`azp`** (não `aud`) contra a allowlist `IAM_ALLOWED_CLIENT_IDS`. Falha em qualquer passo → `401` com envelope AD-14 (`{"error":{"code":"SSO_TOKEN_INVALIDO","message":...}}`); `escreverErro` é local ao pacote `iam` (nunca importa `handlers` — mesmo motivo da duplicação em `middleware/auth.go`). Injeta `email` e `email_verified` no contexto; **não** consome roles/grupos do realm.
- `GET /api/auth/sso/config` (público, sem middleware): lê `IAM_BASE_URL`, `IAM_CLIENT_ID`, `IAM_REDIRECT_URI`, `IAM_ALLOWED_CLIENT_IDS` do ambiente. Se **qualquer uma** faltar → `200 {"enabled":false}` e nada mais. Caso completo → `200 {"enabled":true,"base_url":<realm>,"client_id":...,"redirect_uri":...,"scopes":...}` (`IAM_SCOPES` default `"openid profile email"`). Nenhum valor sensível — é o mesmo dado já visível na URL de authorize de um client público OIDC/PKCE.
- `POST /api/auth/sso/keycloak` (sempre registrado **atrás** do middleware `iam` em `newMux`, nunca exposto direto; **sem corpo** — reusa o header `Authorization` já validado): extrai `email`/`email_verified` do contexto. `email` vazio → `400 VALIDATION_ERROR`. `email_verified != true` → `401` com `code` `EMAIL_NOT_VERIFIED` e mensagem distinta orientando a confirmar o e-mail corporativo (AC4). Busca `usuarios` por `lower(email) = lower($1)`; sem linha → `401` com `code` `SSO_SEM_CONTA` e mensagem orientando a se cadastrar primeiro (AC3) — **nunca cria conta**. Conta encontrada com `ativo=false` → `401 INVALID_CREDENTIALS` (conta desativada não autentica por SSO — coerente com Story 1.8 e epic-context). Caso válido: `services.EmitirSessao(db, jwtSecret, usuario.ID)` (mesmo par access JWT 30min + refresh cookie HttpOnly 2h do login por senha — AD-6, `setRefreshCookie` reusado), resposta `200 {"token":...,"usuario":{id,nome,email,papel}}` byte-compatível com a de `POST /api/auth/login`. O papel é sempre o de `usuarios`, nunca do token. O token do Keycloak nunca é persistido.
- `POST /api/auth/logout` (sem middleware; lê o cookie `refresh_token`): se presente, `services.RevogarSessaoPorRefreshToken` (`UPDATE sessoes SET revogado_em = now() WHERE refresh_token = $1 AND revogado_em IS NULL`); **sempre** limpa o cookie (`clearRefreshCookie`, reusado de `handlers/auth.go`) e responde `204`. Idempotente: cookie ausente ou já revogado também é `204`, nenhuma linha alterada. Não distingue sessão SSO de sessão por senha — o RP-initiated logout é decidido no cliente.
- `iam.Config` carregada uma vez no startup (molde de `services.CarregarEmailConfig`): `IAM_BASE_URL` com barra final removida (`strings.TrimRight(v,"/")`); `IAM_ALLOWED_CLIENT_IDS` split por `,` + `TrimSpace`, descartando vazios. `Habilitado()` = `RealmURL != ""`. `newMux` **sempre** registra `GET /api/auth/sso/config` e `POST /api/auth/logout`; só registra `POST /api/auth/sso/keycloak` (+ constrói `JWKSClient`/middleware) quando `iamCfg.Habilitado()`; com `RealmURL` setado mas allowlist vazia, loga `slog.Warn` (todo login SSO falharia no `azp`).
- Frontend `lib/keycloak/config.ts`: `fetchSSOConfig()` busca `/api/auth/sso/config` uma vez (cache em memória só de sucesso; falha de rede/parse → `{enabled:false}`, **nunca lança**).
- Frontend `lib/keycloak/pkce.ts`: `code_verifier` = 48 bytes aleatórios (`crypto.getRandomValues`) em base64url; `code_challenge` = S256 via `crypto.subtle.digest('SHA-256', ...)` — **desvio deliberado do `FB_APU02`**, que usa `@noble/hashes` por causa de contexto não-seguro; `crypto.subtle` cobre `localhost` (dev) e HTTPS (produção) e evita uma dependência npm nova. `state` = UUID v4 via `getRandomValues`. `verifier`+`state` em `sessionStorage` (`sso_pkce_verifier`/`sso_oauth_state`); `buildLoginUrl(cfg)` monta `{base_url}/protocol/openid-connect/auth?response_type=code&client_id&redirect_uri&scope&state&code_challenge&code_challenge_method=S256`.
- Frontend `lib/keycloak/callback.ts` `trocarCodePorSessao(searchParams)`: valida `state` contra o `sessionStorage` (remove após ler; ausente/divergente → `ErroCallbackSSO('CSRF')`); troca `code`+`verifier` por token no `{base_url}/protocol/openid-connect/token`; então `POST /api/auth/sso/keycloak` com `Authorization: Bearer <keycloak_access_token>`; devolve `{token, usuario}` (mesmo shape do login por senha). Erro do backend → propaga `body.error.code` como `codigo` para a página distinguir "sem conta" de "e-mail não verificado".
- `AuthCallbackPage` (rota pública `/auth/callback`, fora do `AppShell`/`RotaProtegida`): no mount (guard `useRef` contra StrictMode) roda `trocarCodePorSessao`; sucesso → `sessionStorage.setItem('auth_via_sso','1')` + `definirSessao(usuario, token)` + `navigate('/', {replace:true})`; falha → `<p role="alert">` com texto por `codigo` (`SSO_SEM_CONTA` → "cadastre-se primeiro" + `<Link to="/cadastro">`; `EMAIL_NOT_VERIFIED` → "confirme seu e-mail corporativo"; `CSRF`/outros → genérico) + `<Link to="/login">`. Pendente → spinner "Concluindo login via Ferreira Costa...". Nunca cria conta, nunca redireciona automaticamente de volta ao Keycloak.
- `LoginPage`: `useEffect` chama `fetchSSOConfig()` e guarda `ssoHabilitado` (começa escondido). Quando `true`, após o bloco de links existentes, renderiza um `Button variant="outline"` "Entrar com Ferreira Costa" que chama `buildLoginUrl(cfg)` + `window.location.assign(url)`. `enabled:false` ou falha → botão não aparece. O fluxo de senha (form, erros, submit) não muda — continua o caminho padrão visível, **nunca** há auto-redirect.
- `AuthProvider`: novo `logout()` no contexto (guard `useRef` contra duplo logout): `clearAccessToken()`, `setUsuario(null)`, `setEstado('anonimo')`, `void fetch('/api/auth/logout', {method:'POST'})` (best-effort, não aguarda). Se `sessionStorage.getItem('auth_via_sso') === '1'`: `removeItem`, então `fetchSSOConfig()` e, se `enabled`, `window.location.assign('{base_url}/protocol/openid-connect/logout?client_id=...&post_logout_redirect_uri={origin}/login')` (RP-initiated logout, AC5); caso contrário `window.location.assign('/login')`. Sessão por senha → direto para `/login`, sem tocar no Keycloak. `definirSessao` inalterado.
- `AppShell`: item "Sair" no `DropdownMenuContent` do perfil (desktop) e na lista do `Sheet` "Mais" (mobile), abaixo do link de perfil, separado por `<hr>` — um `<button>` que chama `logout()` do `useAuth()`, com texto/`aria-label` "Sair".
- Erros novos do backend saem do vocabulário AD-14 estendido com dois `code` específicos de SSO (`SSO_SEM_CONTA`, `EMAIL_NOT_VERIFIED`) + `SSO_TOKEN_INVALIDO` (middleware) — documentados nesta spec; o restante reusa `VALIDATION_ERROR`/`INVALID_CREDENTIALS`/`INTERNAL_ERROR`. Handlers reusam `escreverErro`/`escreverJSON`/`erroEnvelope` (handlers/auth.go).
- Testes: `iam/` com `httptest.Server` servindo um JWKS falso montado de uma `*rsa.PrivateKey` gerada no teste, que assina os tokens de teste — nenhuma dependência de Keycloak real ou de rede. `handlers/auth_sso_test.go` exercita a Matrix na fronteira HTTP com o middleware `iam` real apontado para o JWKS falso. `main_test.go` cobre o registro condicional em `newMux`. Frontend: `pkce`/`config`/`callback` com `crypto.subtle` real (Node 22) e `fetch`/`sessionStorage` stubados; `LoginPage`/`AuthCallbackPage`/`AppShell`/`auth` com `vi.stubGlobal('fetch')` e `sessionStorage`.

**Block If:** nenhuma decisão **de design** desta story depende de aprovação humana. A dependência do provisionamento real do client Keycloak no realm `ferreiracosta` (client id dedicado, redirect URIs, post-logout URI, env vars de deploy) é ação de operador conhecida (PRD §11 Open Questions 5 e 6; ARCHITECTURE-SPINE "Deferred" — "requer aprovação humana explícita"). Implementar e testar tudo com fakes, então finalizar em `status: awaiting-operator` com `operator_actions`. **Nunca** usar `blocked` para isso.

**Never:**
- Nenhuma migration nova; nenhum campo novo em `usuarios`/`sessoes`.
- SSO **nunca cria conta** nem define/atualiza papel; nunca consome roles/grupos do Keycloak (mesma lacuna do `FB_APU02`, extensão futura).
- Nenhum auto-redirect da tela de Login para o Keycloak; login por senha continua o caminho padrão visível (desvio deliberado do `FB_APU02`, addendum §B).
- O token do Keycloak nunca é persistido nem reusado após a troca; nunca aparece em query string / log.
- Nenhuma biblioteca `keycloak-js`; **nenhuma dependência npm nova** (`@noble/hashes` do `FB_APU02` substituído por `crypto.subtle`).
- Nenhuma mudança no formato de sessão (AD-6), em `RankPapel`, em `middleware/auth.go` (`RequireAuth`), ou nos handlers/serviços de login por senha — SSO e logout reusam `EmitirSessao`/`setRefreshCookie`/`clearRefreshCookie` sem alterá-los.
- Nenhum MFA no caminho SSO (o realm já impõe — epic-context / PRD §4.1); nenhuma tela de "método de login" em Configurações (não é AC desta story).
- Nenhum rate-limit no endpoint de troca (o `FB_APU02` tem; é escopo da Story 1.10, que ainda não existe).
- Nenhuma normalização de `iss` além de remover a barra final; nenhum tratamento de refresh token do Keycloak (só o access token é trocado).

**Acceptance Criteria:**
- Given a tela de Login com `/api/auth/sso/config` retornando `enabled:true`, when ela renderiza, then e-mail/senha aparece como caminho padrão e o botão "Entrar com Ferreira Costa" aparece como opção adicional, sem nenhum redirecionamento automático para o Keycloak.
- Given `/api/auth/sso/config` retornando `enabled:false` ou indisponível, when a tela de Login renderiza, then nenhum botão de SSO aparece e o login por senha segue funcional.
- Given um token RS256 válido do realm configurado (`iss` correto, `azp` na allowlist, `email_verified:true`) cujo e-mail casa (case-insensitive) com uma conta ativa, when `POST /api/auth/sso/keycloak` processa a troca, then a resposta é `200` com o mesmo par de tokens de sessão do login por senha (access no corpo, refresh em cookie HttpOnly), nenhuma conta é criada, e `usuario.papel` é o valor de `usuarios` (não do token).
- Given um token válido cujo e-mail não tem conta local, when a troca é processada, then a resposta é `401` com `code` `SSO_SEM_CONTA` e mensagem orientando o cadastro; and given `email_verified:false` com conta existente, then a resposta é `401` com `code` `EMAIL_NOT_VERIFIED` e mensagem distinta.
- Given um token cuja assinatura não é RS256, ou com `iss`/`azp` inválidos, ou sem `Authorization`, when a requisição chega em `POST /api/auth/sso/keycloak`, then o middleware `iam` responde `401` e `KeycloakSSOHandler` nunca executa.
- Given `IAM_BASE_URL` não definido, when o servidor sobe, then `GET /api/auth/sso/config` responde `{"enabled":false}`, `POST /api/auth/sso/keycloak` não existe (`404`) e `POST /api/auth/logout` continua registrado.
- Given uma sessão iniciada via SSO (marca `auth_via_sso`), when o usuário aciona "Sair", then a sessão local é encerrada (`accessToken` limpo, estado `anonimo`, `POST /api/auth/logout` revoga a linha em `sessoes`) e o navegador é levado ao endpoint de RP-initiated logout do Keycloak com `post_logout_redirect_uri` de volta para `/login`; and given uma sessão por senha, then "Sair" encerra a sessão local e vai para `/login` sem tocar no Keycloak.
- Given o fluxo de callback em `/auth/callback` com `state` divergente do armazenado, when a página monta, then nenhuma sessão é estabelecida e uma mensagem de erro (possível CSRF) é exibida com link para `/login`.

- **Desvios deliberados do `FB_APU02`** (AD-7 / addendum §B): (1) sem auto-redirect no Login — botão adicional; (2) `crypto.subtle` no lugar de `@noble/hashes` — cobre `localhost` + HTTPS, zero dependência nova; ambiente de dev acessado por IP de LAN sobre HTTP puro não terá o botão funcional (aceitável para ferramenta interna, documentar); (3) mensagem "cadastre-se primeiro" em vez de "contate o administrador"; (4) `log/slog` no lugar de `log`.
- **Dívidas do `FB_APU02` NÃO repetidas** (addendum §B, "não repetir sem decisão consciente"): JWKS vazio/erro tratado como falha (não "sucesso com cache vazio que trava login por 1h"); `iss` normalizado (barra final); refetch de JWKS no máximo 1× por `GetKey` que erra o cache (sem amplificação por `kid` arbitrário).
