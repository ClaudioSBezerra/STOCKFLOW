- (decision) Paradigma: Layered Go pragmático (handlers -> services -> acesso a dados via database/sql, sem ORM), ratificado a partir do código real do FB_APU02 -- não Hexagonal/Clean como no PRD-fonte anterior. Binds: todo o backend. Prevents: introdução de camadas de portas/adaptadores ou framework web divergente entre stories construídas independentemente.
- (decision) Stack backend ratificada do FB_APU02: Go stdlib net/http (sem chi/gorilla), PostgreSQL 15, sem ORM. Frontend: React 18 + TypeScript + Vite + shadcn/ui + Tailwind + React Router 6 + TanStack Query 5 + React Hook Form + Zod -- mesma stack do FB_APU02, conforme instrução explícita do usuário.
- (decision) [ADOPTED] Redis e RabbitMQ NÃO fazem parte do stack do stockflow -- diferente do FB_APU02 (que mantém Redis no compose sem uso real) e do PRD-fonte original (que exigia RabbitMQ). Simplificação deliberada: nenhuma decisão de arquitetura deste projeto depende de Redis ou RabbitMQ (ver AD de tempo real, e-mail assíncrono e cache de papel abaixo).
- (decision) Tempo real (substituto do onSnapshot): broadcaster in-process + SSE, confirmado com o usuário. Binds: eventos de domínio (produto criado/editado, estoque alterado, pedido aprovado) que precisam empurrar atualização para clientes conectados. Prevents: introdução de Redis Pub/Sub ou WebSocket por divergência entre stories. Rule: um registry in-memory de conexões SSE abertas por processo; evento de domínio publicado localmente (função Go, não fila) notifica os assinantes; cliente sempre faz GET completo ao reconectar (nunca replay de eventos perdidos). Constraint explícita: só funciona corretamente com uma única instância da aplicação rodando -- se o deploy escalar horizontalmente no futuro, esta decisão precisa ser revisitada (Redis Pub/Sub volta à mesa).
- (decision) E-mail assíncrono (verificação de conta FR-3, redefinição de senha FR-32): tabela de outbox no Postgres (ex. emails_pendentes) + worker goroutine com polling, em vez de fila RabbitMQ. Rule: toda escrita que precisa enviar e-mail insere na tabela de outbox na MESMA transação da escrita de negócio (nunca envia SMTP síncrono dentro do handler HTTP); worker consome e marca enviado/falho com retry.
- (decision) Cache/invalidação de papel (FR-31 revogação imediata de acesso): SEM cache -- papel do Usuário é lido diretamente do Postgres a cada requisição autenticada (dentro do middleware de autorização). Rule: nenhum cache de papel em memória ou Redis; simplicidade e correção imediata > latência marginal, dado volume de uso de ferramenta interna.
- (version) Biblioteca de PDF (FR-26): signintech/gopdf, confirmado com o usuário após pesquisa web (2026-08-29) -- gofpdf (jung-kurt) arquivado em 2021, go-pdf/fpdf arquivado em 2025, Maroto v2 depende transitivamente do gofpdf arquivado. gopdf é pure Go, mantido ativamente, ~2.9k stars. Verificar versão exata (go.mod) no momento da implementação, não fixar aqui.
- (decision) Modelo de sessão (FR-1): reaproveitar padrão do FB_APU02 -- JWT de acesso curto (30min, golang-jwt/jwt/v5) + refresh token rotativo em cookie HttpOnly, mas com TTL do refresh ajustado para 2h (em vez de 7 dias) para expressar 'expira por inatividade' de FR-1. Rotação a cada uso do refresh (mesma janela desliza). Confirmado com o usuário.
- (decision) [ADOPTED] Keycloak SSO (FR-34): replicar desenho técnico do FB_APU02 documentado em addendum.md §B do PRD -- pacote iam/ dedicado, JWKS cache em memória TTL 1h, validação RS256 via kid, iss = URL do realm, azp (não aud) contra allowlist IAM_ALLOWED_CLIENT_IDS, email_verified obrigatório, busca de usuário por e-mail case-insensitive, nunca cria conta nova, endpoint de troca de token emite os mesmos tokens de sessão próprios (ver AD de modelo de sessão), endpoint de config runtime (não build-time) para a mesma imagem servir ambientes com/sem SSO, RP-initiated logout. Divergência deliberada do FB_APU02: login por senha continua sendo o caminho padrão visível (sem auto-redirect); client id próprio do stockflow no mesmo realm ferreiracosta.
- (decision) [ADOPTED] Autorização por papel (FR-2): hierarquia usuario<almoxarife<gestor<adm com herança estrita, checada em middleware central (nunca ad-hoc no handler), três formas por rota: papel mínimo exigido / comparação relativa ao alvo da ação (ex. gestor só age sobre almoxarife/usuario) / filtro de escopo em listagem (ex. FR-24 usuario sem papel almoxarife+ recebe só os próprios pedidos, nunca 403). Binds: todos os endpoints. Prevents: checagem de papel inconsistente ou esquecida entre handlers construídos independentemente.
- (decision) [ADOPTED] Dimensões de Produto (FR-8, FR-10, FR-17): sempre par estruturado {valor: numeric, unidade: enum}, nunca string livre -- por dimensão (comprimento, largura, diametro, altura, espessura, lateral). Binds: schema de produtos, validação de cadastro/importação, ferramenta de Normalização. Prevents: reintrodução do parsing de texto livre (achado de débito técnico E.9 do addendum).
- (decision) [ADOPTED] Concorrência de estoque (FR-14, FR-15, FR-25): toda escrita que debita/transfere/aprova usa SELECT ... FOR UPDATE (lock pessimista) dentro da mesma transação; ordem canônica de lock (produto_id, estoque_id) ascendente para evitar deadlock entre transações concorrentes. Prevents: saldo negativo ou deadlock por ordem de lock inconsistente entre stories construídas independentemente.
- (decision) [ADOPTED] Fotos de Produto (FR-27, FR-28): armazenadas em disco, volume Docker nomeado e persistente (não storage de objetos externo, não base64 inline) -- mesma resolução (500px maior lado) e compressão (JPEG q=0.82) independente do fluxo. Soft-delete de Produto via deleted_at IS NULL em todo read; produto soft-deleted nunca reentra em mesclagem de duplicatas (FR-20), mas mantém foto em disco para auditoria permanente.
- (decision) Bootstrap do primeiro Adm (FR-3): via comando CLI dedicado (ex. cmd/seed-admin), nunca endpoint HTTP -- ratifica o padrão do PRD-fonte original, ainda válido independente do stack de mensageria.
- (decision) Topologia de deployment: Docker Compose single-host no padrão installer/cliente-aws do FB_APU02 (servidor dedicado dentro da Ferreira Costa, já com Keycloak habilitado) -- serviços: api (Go), web (React + Nginx), db (postgres:15-alpine). SEM Redis, SEM RabbitMQ (ver decisões acima). Volume nomeado persistente para fotos. Endereço/DNS exato do servidor permanece Deferred -- item de infraestrutura, não de arquitetura de aplicação.
- (decision) Convenção de nomenclatura: tabelas/campos do banco em português, nomes de domínio já estabelecidos pelo protótipo e pelo PRD (produtos, estoques, pedidos, movimentacoes, usuarios, solicitacoes_promocao, etc.) -- não traduzir para inglês. Nomes de pacotes/tipos Go em inglês (convenção Go idiomática), mas nomes de coluna/tabela em português. Prevents: mistura inconsistente de idioma no schema entre stories.
- (decision) IDs: UUID v4 como chave primária em todas as tabelas novas (não serial incremental) -- evita colisão/reindexação ao migrar de IDs de documento do Firestore (strings não sequenciais) e não vaza contagem de registros. Datas: timestamptz em UTC no banco, formatado ISO 8601 na API.
- (decision) Logging estruturado: log/slog da stdlib Go (não zap) -- ratifica a adaptação já feita no FB_APU02 (comentários em iam_auth_middleware.go documentam troca de zap por log stdlib). Envelope de erro HTTP: {"error": {"code": string, "message": string}} consistente em toda a API.
- (assumption) MFA (FR-37, login por senha para gestor/adm): biblioteca TOTP em Go ainda não verificada/escolhida -- não vincular aqui; verificar opção atual mantida (candidata conhecida: pquerna/otp) no momento da implementação da story, não nesta spine.
- (question) Endereço/DNS exato do servidor de deploy em Ferreira Costa e client id definitivo a provisionar no realm Keycloak ferreiracosta permanecem em aberto -- infraestrutura/provisionamento real exige aprovação humana explícita antes de qualquer ação, fora do escopo desta spine.
- (decision) Migração de dados: script one-off (não parte do runtime da aplicação) lendo diretamente do PostgreSQL espelho do Firestore mantido pela empresa -- converte dimensões texto-livre para {valor,unidade} estruturado, gera UUIDs novos com tabela de mapeamento id-antigo->id-novo para preservar referências entre Produtos/Estoques/Movimentacoes/Pedidos/Usuarios, popula NOMENCLATURA_TEMPLATES (28 seeds) e CATEGORIAS (25 seeds) do addendum.md §G/§H. Corte único, sempre disparado por humano (nunca por agente autônomo, já vinculante desde o PRD §9).
