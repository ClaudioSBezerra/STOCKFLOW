- (decision) Paradigma: Layered Go pragmático (handlers -> services -> acesso a dados via database/sql, sem ORM), ratificado a partir do código real do FB_APU02 -- não Hexagonal/Clean como no PRD-fonte anterior. Binds: todo o backend. Prevents: introdução de camadas de portas/adaptadores ou framework web divergente entre stories construídas independentemente.
- (decision) Stack backend ratificada do FB_APU02: Go stdlib net/http (sem chi/gorilla), PostgreSQL 15, sem ORM. Frontend: React 18 + TypeScript + Vite + shadcn/ui + Tailwind + React Router 6 + TanStack Query 5 + React Hook Form + Zod -- mesma stack do FB_APU02, conforme instrução explícita do usuário.
- (decision) [ADOPTED] Redis e RabbitMQ NÃO fazem parte do stack do stockflow -- diferente do FB_APU02 (que mantém Redis no compose sem uso real) e do PRD-fonte original (que exigia RabbitMQ). Simplificação deliberada: nenhuma decisão de arquitetura deste projeto depende de Redis ou RabbitMQ (ver AD de tempo real, e-mail assíncrono e cache de papel abaixo).
- (decision) Tempo real (substituto do onSnapshot): broadcaster in-process + SSE, confirmado com o usuário. Binds: eventos de domínio (produto criado/editado, estoque alterado, pedido aprovado) que precisam empurrar atualização para clientes conectados. Prevents: introdução de Redis Pub/Sub ou WebSocket por divergência entre stories. Rule: um registry in-memory de conexões SSE abertas por processo; evento de domínio publicado localmente (função Go, não fila) notifica os assinantes; cliente sempre faz GET completo ao reconectar (nunca replay de eventos perdidos). Constraint explícita: só funciona corretamente com uma única instância da aplicação rodando -- se o deploy escalar horizontalmente no futuro, esta decisão precisa ser revisitada (Redis Pub/Sub volta à mesa).
- (decision) E-mail assíncrono (verificação de conta FR-3, redefinição de senha FR-32): tabela de outbox no Postgres (ex. emails_pendentes) + worker goroutine com polling, em vez de fila RabbitMQ. Rule: toda escrita que precisa enviar e-mail insere na tabela de outbox na MESMA transação da escrita de negócio (nunca envia SMTP síncrono dentro do handler HTTP); worker consome e marca enviado/falho com retry.
- (decision) Cache/invalidação de papel (FR-31 revogação imediata de acesso): SEM cache -- papel do Usuário é lido diretamente do Postgres a cada requisição autenticada (dentro do middleware de autorização). Rule: nenhum cache de papel em memória ou Redis; simplicidade e correção imediata > latência marginal, dado volume de uso de ferramenta interna.

- (decision) Modelo de sessão (FR-1): reaproveitar padrão do FB_APU02 -- JWT de acesso curto (30min, golang-jwt/jwt/v5) + refresh token rotativo em cookie HttpOnly, mas com TTL do refresh ajustado para 2h (em vez de 7 dias) para expressar 'expira por inatividade' de FR-1. Rotação a cada uso do refresh (mesma janela desliza). Confirmado com o usuário.
- (decision) [ADOPTED] Keycloak SSO (FR-34): replicar desenho técnico do FB_APU02 documentado em addendum.md §B do PRD -- pacote iam/ dedicado, JWKS cache em memória TTL 1h, validação RS256 via kid, iss = URL do realm, azp (não aud) contra allowlist IAM_ALLOWED_CLIENT_IDS, email_verified obrigatório, busca de usuário por e-mail case-insensitive, nunca cria conta nova, endpoint de troca de token emite os mesmos tokens de sessão próprios (ver AD de modelo de sessão), endpoint de config runtime (não build-time) para a mesma imagem servir ambientes com/sem SSO, RP-initiated logout. Divergência deliberada do FB_APU02: login por senha continua sendo o caminho padrão visível (sem auto-redirect); client id próprio do stockflow no mesmo realm ferreiracosta.
- (decision) [ADOPTED] Autorização por papel (FR-2): hierarquia usuario<almoxarife<gestor<adm com herança estrita, checada em middleware central (nunca ad-hoc no handler), três formas por rota: papel mínimo exigido / comparação relativa ao alvo da ação (ex. gestor só age sobre almoxarife/usuario) / filtro de escopo em listagem (ex. FR-24 usuario sem papel almoxarife+ recebe só os próprios pedidos, nunca 403). Binds: todos os endpoints. - (decision) AD-25 rationale: expiração automática de reserva foi cogitada e descartada -- introduziria um mecanismo assíncrono novo (o sistema hoje só tem o worker de e-mail, AD já existente) e o que fazer com o Pedido quando a reserva expira é ambíguo (auto-rejeitar? deixar pendente sem reserva, reabrindo a race?).
